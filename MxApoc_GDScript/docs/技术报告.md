MaximumApocalypse · 技术报告

JSON 数据驱动下的异步事件与动画阻塞
解释 noname 与本项目在 await 行为上的差异，并记录已发现的结算延迟根因与修复范围。

核心结论
JSON 本身不会决定是否需要 await。决定因素是 JSON 内容最终由什么执行器解释，以及游戏操作是否返回可追踪的异步事件。
一页摘要
本项目的 JSON content 会被编译成 GDScript 函数。GDScript 不会自动等待函数内部启动的协程，因此异步操作必须显式 await。

已确认的典型问题包括：外星人攻击销毁卡牌，以及僵尸步行者（精英）触发额外抓怪物牌。

修复策略是让怪物 JSON 中的 damage、discard、remove_card、draw_monster 调用全部加入 await，并检查同类数据。

1. 两种事件模型的差异
MaximumApocalypse
JSON content → CodeExecutor → GDScript Callable

func _fn(player, target, event, game) -> void:
    target_player.remove_card(card)
外层只等待 content.call()。内部调用若没有 await，就会脱离当前结算链。

noname
技能 content → GameEvent / Promise → 事件链调度器

async content(event, trigger, player) {
    await player.draw().forResult();
}
当前版本同样使用 async/await；旧版本常见的是 generator/yield。看起来“不写 await”的代码不一定代表操作是同步的。

2. 本项目的实际调用链
Entity.trigger()
  └─ await Skill.execute_content()
       └─ await content.call()
            └─ await player.remove_card()
                 └─ await input.play_card_destroy_animation()
                      └─ 动画完成后 respond_*()
                           └─ 从 hand / equipment_zone 移除卡牌
只有每一层都等待，最内层的动画和实体变更才会阻塞当前怪物行动。

3. 已确认的两个延迟案例
外星入侵者：攻击时销毁卡牌
原始调用

target_player.remove_card(card)
技能代码没有等待异步销毁流程，导致攻击结算与后续状态推进先完成，移出游戏日志延迟出现。

现已改为：

await target_player.remove_card(card)
僵尸步行者（精英）：抓取额外怪物牌
原始调用

event.player.draw_monster(1)
额外抓牌协程没有加入当前抓怪物结算链，因此可能等到后续游戏状态变化才继续。

现已改为：

await event.player.draw_monster(1)

5. 风险与后续建议
当前风险
JSON content 可以调用任意暴露给执行器的对象方法，但编译器不会检查“返回值是否为协程”以及调用方是否等待。这类遗漏只能靠约定、静态扫描或运行时测试发现。

建议的长期方向
1. 为异步游戏操作建立统一命名或元数据标识，例如 async_action。

2. 在 CodeExecutor 测试中加入“技能必须等待实体操作完成”的行为测试。

3. 如果希望 JSON 不再显式写 await，需要把 damage、draw、discard、remove_card 等操作全面事件化，由事件调度器自动串联；这属于较大架构重构。
